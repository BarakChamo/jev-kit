Wrote `map.mjs`. Approach:

- **Code handles exact identifier matching** (rule 6/12): regexes pull candidate emails, phone numbers, and order-id-shaped tokens out of `draft_reply`, then normalized comparison against the recipient's own email/phone/order_ids filters out the recipient's own data. This is a reliable exact comparison, so it's derived in code rather than asked of Jev.
- **Jev judges what needs interpretation**: for each *foreign* candidate, a scoped `noul` asks whether it's actually a personal identifier of a specific individual (exposure) vs. a company contact address/support line/non-order-id code (allowed). A separate `noul` asks whether any other named person appears, explicitly excluding staff introduced by first name only — this is the one signal regex can't get.
- **Gate + abstain**: each `noul` is thresholded (≥0.7 → yes, ≤0.3 → no, else abstain). If any signal is confidently "yes," the case is `yes`; else if any signal is ambiguous, it's `abstain`; otherwise `no`. This keeps false negatives rare (any confident detection wins) while routing genuinely unclear cases to a human instead of guessing.

I manually traced three cases (plain shipping update with own order id; a leaked neighbor's name/email/phone/order id; an email/phone that are legitimate company contacts plus a staff first name) through the extraction logic by hand — the candidate lists and expected classifications came out as intended. I wasn't able to actually execute `node` in this sandbox (Bash approval was blocked), so this is verified by inspection, not by running it — worth a quick real run with `jev-eval` before trusting it on live traffic.
