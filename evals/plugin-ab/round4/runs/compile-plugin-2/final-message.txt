Both files are written to the working directory. Design summary:

**questions.json** — one `noul` question per policy category (hate speech, violent threats, self-harm content, CSAM, harassment, spam, illegal goods), plus a `claims_exemption_context` detector. Each question's `instructions`/`criteria` carries the specific policy rule text — that's the part the LLM compiles from the 12-page doc each time the policy team edits it (per the jev-questions skill, all meaning lives in instructions/criteria, not the question key). The `state` example shows the facts each judgment needs: post text, reply context (parent post, for harassment), light author signals, and a `media_description` slot for a pre-captioned image if the post has media.

**decide.ts** — pure code, no Jev calls. Zero-tolerance CSAM path escalates to a priority queue at a very low threshold, never a plain "remove" and never silently allowed. Other categories gate on the `noul` probability with a remove/review/allow threshold — unsure always goes to review, never to allow. The exemption-claim detector lowers the review floor rather than trusting an "this is satire/reporting" claim to clear a real signal, following the "detector next to a manipulable judgment" pattern.

One thing worth flagging: this is a compiled *draft*, not something to trust at scale yet. Per the skill's architecture rule, whenever the policy doc changes, the LLM should produce a few candidate compilations, they should be scored against ~30 labelled cases (jev-eval), and only the winner gets pinned — never recompile at request time. I didn't build that eval harness here since the task was just the request shape and decision logic; want me to add it next?
